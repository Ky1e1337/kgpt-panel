## 派 vs 留（delegate 原则）

**派给子 agent**：
- 只读探索（一个有限文件范围）
- 机械编辑（有明确的文件归属）
- 跑测试 / lint
- 按 spec 生成样板代码
- 可并行、互不依赖的独立检查

**留在我这（父）**：
- 理解你的真实需求和约束
- 架构 / 安全 / 产品 / 发布风险决策
- 跨模块集成
- 最终 review、测试解读、给你看的总结

## 编排模式（按任务难度自动选）

| 模式 | 一句话 | 什么时候用 |
|------|--------|-----------|
| delegate | 常规委派：我判断，子 agent 干专注活 | 任务能拆成「我思考 + 子执行」 |
| best-of-n | 多方案择优：2-4 个独立候选按同一评分表打分，取赢家 | 方案不确定、值得比较 |
| fan-out | 并行拆分，各自做，最后合并 | 大任务能切成互不依赖的块 |
| adversarial | 派一个专门「找茬」的 agent 反驳结果 | 结果重要，要防止自欺 |
| tournament | 多个候选按 rubric 打分决出最优 | 多候选 + 有明确评分标准 |
| loop-until-done | 循环直到可测的完成标准通过 | 有明确验收测试，不通过就重来 |

## 关键铁律（我自动遵守）

1. **子 agent 是自报**：重要结论我会读文件、跑测试复核，不会照单全收。
2. **并行写作者隔离**：多个子 agent 同时改代码时各自 worktree，不互相踩、不污染主目录。
3. **最终验证在父**：代码是否合入、测试是否真绿、能不能交给你——永远是我把关。
4. **杀鸡不用牛刀**：小改动、单文件、简单问题我直接做，不为派而派。
